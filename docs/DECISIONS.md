# Принятые решения и отклонения от документации

Документ фиксирует решения, принятые при реализации MVP, и места, где реализация
 conscious расходится с исходными документами (`01`–`11`).

---

## Д1. Локальный запуск без Docker

**Решение.** Проект запускается напрямую в Windows: Python-venv + FastAPI на порту 8000,
Vite- dev-сервер на 5173, PostgreSQL как локальная служба.

**Причина.** `03_ARCHITECTURE.md` и `02_PRD.md` упоминают Docker Compose как способ
локального развёртывания. По условиям задачи Docker запрещён и не устанавливался.

**Что сделано вместо.** Скрипты `scripts/setup.ps1`, `scripts/run-backend.ps1`,
`scripts/run-frontend.ps1` и `scripts/init_db.sql` повторяют роль Compose: подготовка
БД, миграции, запуск обоих сервисов. Архитектура кода не привязана к контейнерам:
конфигурация идёт через переменные окружения, файлы — через `STORAGE_DIR`, пути
вычисляются от корня проекта. При появлении Podman Compose-файл можно добавить без
изменения кода.

---

## Д2. PostgreSQL как основная БД

**Решение.** Используется PostgreSQL 18 (локальная служба Windows), как и указано в
`03_ARCHITECTURE.md`. Роль `oapv_app` и базы `obeshchanie` / `obeshchanie_test` создаются
идемпотентным скриптом `scripts/init_db.sql`.

**Причина.** Требование задачи: не подменять PostgreSQL SQLite молча.

**Деталь про переносимость.** JSON-поля описаны как `JSON().with_variant(JSONB, "postgresql")`,
поэтому при необходимости схема переносится на SQLite без изменения кода. Миграции
Alembic работают на обеих СУБД. Текущий режим — PostgreSQL.

---

## Д3. Собственный формат ошибок API

**Решение.** Все ошибки возвращаются в формате
`{"error": {"code", "message", "details"}}` — как в `05_API_CONTRACT.md`. Traceback, SQL и
секреты наружу не выводятся; в логи попадает только факт ошибки.

**Дополнение сверх контракта.** Коды ошибок (`VALIDATION_ERROR`, `NOT_FOUND`,
`UNAUTHORIZED`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE` и др.) вынесены в
`app/core/errors.py` и используются единообразно, включая перехват ошибок валидации
Pydantic и необработанных исключений.

---

## Д4. Аутентификация

**Решение.** Регистрация и вход по электронной почте и паролю, плюс демо-вход.
Пароли хешируются PBKDF2-HMAC-SHA256 (240 000 итераций) — только стандартная библиотека.
Сессия — подписанный HMAC-SHA256 токен в `localStorage`, срок жизни 14 дней.

**Почему так.** `02_PRD.md` требует «минимальную аутентификацию или безопасный локальный
demo-mode». Внешние библиотеки для JWT и паролей не добавлялись: `passlib`/`bcrypt`
требуют отдельной компиляции на Windows, а задача не предполагает криптографического
аудита. Реализация покрыта тестами на изоляцию рабочих пространств.

**Отличие от документации.** В контракте (`05_API_CONTRACT.md`) блок авторизации не
описан; маршруты добавлены как `POST /api/v1/auth/register`, `/auth/login`, `/auth/demo`,
`GET /api/v1/auth/me`.

---

## Д5. Модель «системных» источников

**Решение.** Описание товара и таблица характеристик автоматически сохраняются как
источники типов `product_description` и `attribute_sheet` и обновляются при каждом
изменении товара.

**Причина.** Требование `02_PRD.md` FR-07: каждая находка должна ссылаться на источник.
Без «системных» источников числовое расхождение невозможно показать с двумя
основаниями (текст продавца + характеристика).

---

## Д6. Что считается «прямым расхождением»

**Решение.** `direct_conflict` создаётся, когда значение из текста продавца и значение из
таблицы характеристик относятся к одному параметру, приведены к одной единице и
отличаются за пределами допуска (3 %).

**Почему не шире.** `04_CLAIM_EVIDENCE_MODEL.md` требует не заявлять о прямом
противоречии, когда условия измерения неизвестны. Поэтому:

* если в тексте есть указание на условия («при полной зарядке», «при температуре …») —
  выдаётся `needs_human_review`;
* если значения приблизительные («около 30 часов») — тоже `needs_human_review`;
* отзывы никогда не дают `direct_conflict` — только `review_signal`;
* документ с областью применения, отличной от модели товара, не сравнивается с
  характеристиками — для него создаётся `document_scope_mismatch`.

**Как определяется «тот же параметр».** Число сопоставляется с характеристикой только
если в тексте рядом с числом есть маркеры именно этой характеристики («батарея»,
«время работы», «вес»). Общих слов («часы», «граммы») недостаточно: иначе «гарантия
24 месяца» сравнивалась бы с «ответ в течение 1 часа».

## Д7. Провайдер ИИ

**Решение.** Интерфейс `ClaimAnalysisProvider` с тремя реализациями:
`MockAnalysisProvider` (по умолчанию, без сети), `OllamaProvider` (локальные модели с
открытыми весами) и `OpenAICompatibleProvider` (любой OpenAI-совместимый API).

**Роль провайдера ограничена.** Он уточняет тип утверждений, которые не распознала
эвристика, и может предложить дополнительные находки. Детерминированные проверки от
него не зависят: при недоступности внешнего сервиса система явно сообщает об этом и
продолжает работу на `mock` (`run_provider` в `app/providers/registry.py`).

**Доверие к загруженным текстам.** Текст документов и отзывов помечается как
недоверенные данные в системной инструкции модели; у модели нет инструментов, доступа к
shell, БД и внешним URL.

## Д8. Архивирование находок при повторной проверке

**Решение.** При новом запуске анализа нерассмотренные авто-находки (`open`,
`in_review`) помечаются `archived = true` и исключаются из основного списка; находки, по
которым человек уже принял решение, остаются видимыми вместе с историей.

**Причина.** Без этого повторная проверка давала бы дубликаты и раздувала список.
История решений при этом не теряется: `ReviewAction` хранится независимо.

---

## Д9. Формат отчёта

**Решение.** Отчёт — HTML, генерируемый на сервере шаблоном Jinja2 с включённым
автоэкранированием. Во frontend он показывается в `iframe` с `sandbox="allow-same-origin"`.
Кнопка «Печать / PDF» открывает системный диалог печати.

**Отличие от документации.** `02_PRD.md` допускает PDF на более позднем этапе — он и не
входит в MVP. Дисклеймер из FR-09 присутствует в отчёте, на странице отчёта и на главной
странице.

---

## Д10. Хранение файлов

**Решение.** Загруженные файлы сохраняются под случайным именем (UUID + расширение) в
`STORAGE_DIR/<product_id>/`. Исходное имя файла хранится только как отображаемое поле
`source_name` и никогда не используется как путь. API не отдаёт `file_path` наружу.

**Причина.** Требования `07_SECURITY_PRIVACY.md` (пункты 4 и 5).

---

## Д11. Тестовая база

**Решение.** Тесты backend работают на отдельной базе `obeshchanie_test`; каждая сессия
тестов откатывает транзакцию, поэтому данные не накапливаются. Схема тестовой базы
создаётся миграциями Alembic — это одновременно проверяет работоспособность миграций.

**Причина.** Требование «отсутствие потери существующих данных» и безопасность рабочих
данных пользователя.

---

## Д12. Расширение API сверх контракта

Контракт (`05_API_CONTRACT.md`) не описывал ряд операций, необходимых для MVP из
`02_PRD.md`. Добавлены:

| Маршрут | Назначение |
|---|---|
| `GET /api/v1/overview` | сводка для главной страницы |
| `GET /api/v1/settings/ai` | состояние ИИ-провайдера и лимиты |
| `POST /api/v1/demo/seed` | добавить демо-товар в текущее пространство |
| `POST /api/v1/products/{id}/sources/manual` | ручной ввод источника |
| `GET /api/v1/sources/{id}/text` | полный текст источника |
| `GET /api/v1/products/{id}/claims` | список утверждений |
| `POST /api/v1/products/{id}/claims` | ручное утверждение |
| `PATCH /api/v1/claims/{id}`, `DELETE /api/v1/claims/{id}` | правка утверждений |
| `GET /api/v1/products/{id}/evidence` | доказательства |
| `GET /api/v1/products/{id}/summary` | сводка по товару |
| `GET /api/v1/reviews/history` | история решений по пространству |
| `GET /api/v1/reviews/overview` | список проверок по пространству |

Все маршруты под `/api/v1`, формат ошибок соответствует контракту.
