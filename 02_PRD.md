# Product Requirements Document --- MVP

## 1. Роли

-   `user`: создаёт и анализирует товары в собственном рабочем
    пространстве.
-   `admin`: локальная административная роль для технического
    обслуживания. Не делать открытый публичный админ-аккаунт с известным
    паролем.

## 2. Основные сущности

-   Workspace
-   Product
-   SourceDocument
-   Claim
-   Evidence
-   Finding
-   ReviewAction
-   AnalysisRun

## 3. Функциональные требования

### FR-01 Создание товара

Пользователь может создать товар с названием, категорией (необязательная
строка), маркетплейсом (Ozon/Wildberries/other), SKU/артикулом
(необязательно), описанием и структурированными характеристиками.

Критерии приёмки: - обязательное название; - валидация длины полей; -
пользователь видит сообщение об ошибке, а не traceback; - товар
сохраняется и появляется в списке.

### FR-02 Импорт источников

Пользователь может загрузить PDF, TXT, CSV, XLSX, PNG/JPG в зависимости
от реализованной поддержки. - На первом этапе обязательно поддержать
TXT, CSV и PDF с извлекаемым текстом. - Для сканированных PDF и
изображений можно сообщить, что нужен OCR, и оставить OCR отдельной
задачей. - Ограничить размер файла конфигурацией. - Сохранять имя, MIME
type, размер, время загрузки и хеш содержимого.

Критерии приёмки: - неподдерживаемый формат отклоняется с понятным
сообщением; - файл не исполняется; - путь файла не берётся напрямую из
имени пользователя; - файл связан с конкретным товаром и рабочим
пространством.

### FR-03 Извлечение утверждений

Система формирует кандидаты на утверждения из описания и источников. У
каждого кандидата: - текст утверждения; - тип; - место/фрагмент
источника; - метод извлечения; - confidence, если его возвращает модель,
с пояснением, что это оценка модели, а не вероятность истины.

Пользователь может отредактировать, подтвердить или отклонить кандидат.

### FR-04 Детерминированная проверка чисел

Система должна обнаруживать простые расхождения между нормализованными
значениями характеристик и числовыми утверждениями. - Нормализовать
единицы только для поддерживаемых измерений. - Не сравнивать разные
величины без явного правила. - Если единицы или условия измерения
неясны, помечать `needs_review`.

### FR-05 Анализ документов

Для каждого документа можно сохранить тип, номер/название, дату
документа (если пользователь указал), дату окончания действия (если
применимо и указана), модель/товар, к которому он относится, и
текст/извлечённые сведения. Не заявлять, что документ действителен
юридически, если это не проверено внешним источником.

### FR-06 Анализ отзывов

Отзывы импортируются из пользовательского файла или вводятся вручную.
Каждый отзыв хранит источник, дату (если есть) и текст. Система может
классифицировать отзыв как положительный/отрицательный/смешанный/неясный
по конкретному аспекту, но должна сохранять исходный фрагмент. Не
выдавать единичный отзыв за статистически значимое доказательство.

### FR-07 Findings

Поддерживаемые виды: - `direct_conflict`: прямое противоречие между
источниками; - `missing_evidence`: для проверяемого утверждения не
предоставлено подтверждение; - `review_signal`: отзывы содержат
возможный сигнал; - `ambiguous_claim`: утверждение слишком расплывчато
для объективной проверки; - `document_scope_mismatch`: документ может
относиться к другой модели/версии; - `needs_human_review`: данных
недостаточно или вывод неоднозначен.

Каждое finding содержит: - заголовок; - тип; - приоритет; - описание; -
ссылку на связанные claims/evidence; - исходные цитаты/фрагменты; -
ограничение/альтернативное объяснение; - рекомендованное действие; -
статус рассмотрения.

### FR-08 Управление статусами

Статусы: `open`, `in_review`, `resolved`, `not_an_issue`,
`insufficient_data`. Любое изменение статуса создаёт запись истории с
пользователем, временем, предыдущим и новым статусом, комментарием.

### FR-09 Отчёт

Отчёт содержит сведения о товаре, дату анализа, источники, список
утверждений, предупреждения, решения пользователя и ограничения анализа.
Экспорт не должен включать секреты, пароли или внутренние токены. В
отчёте всегда есть пометка: «Автоматический анализ помогает выявлять
возможные несоответствия и не является юридическим заключением или
независимым испытанием товара».

### FR-10 Демонстрационные данные

Добавить синтетический пример товара с явно маркированными вымышленными
данными. В UI и отчёте должно быть видно, что это демонстрационный
пример.

## 4. Нефункциональные требования

-   типизация на фронтенде и бэкенде;
-   миграции БД;
-   тесты ключевой логики;
-   единый формат ошибок;
-   логирование без паролей, API-ключей и полного содержимого личных
    документов;
-   конфигурация через `.env`, `.env.example` без реальных секретов;
-   воспроизводимый локальный запуск через Docker Compose;
-   базовая защита от доступа к чужим товарам;
-   доступность основных функций без внешнего ИИ-API через mock/demo
    provider.

## 5. Приоритеты

P0: CRUD товара, импорт TXT/CSV, модель источников, числовые проверки,
findings, история, тесты. P1: PDF-текст, подключаемый ИИ-провайдер,
HTML-отчёт. P2: PDF-экспорт, OCR, импорт по URL без обхода ограничений,
дополнительные форматы.

## 6. Критерии готовности MVP

-   свежий клон запускается по инструкции;
-   миграции проходят на чистой БД;
-   тесты проходят;
-   можно создать товар, добавить источники и получить хотя бы
    детерминированные findings;
-   каждое finding объяснимо и связано с источником или явно указывает
    на отсутствие источника;
-   демонстрационные данные не выдаются за реальные;
-   ошибки не приводят к падению приложения без понятного сообщения.
